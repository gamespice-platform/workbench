# GameSpice Workbench

Admin live-edit surface over GameSpice Core's `GSProfileRuntime`: a transport-agnostic JSON API (`GSWorkbenchApi`), and `GSWorkbenchHttp`, the off-by-default loopback HTTP adapter (bearer token, `/api/profiles` routes, `web/index.html`) on GameSpice Core's `GSHttpServer`. Read [docs/design.md](docs/design.md) first; it records what the family already has (no HTTP server) and what is not built.

**The distributable is `addons/gs_workbench/`.** `project.godot` and `examples/` exist to validate it alone. It requires gs-core (`ln -s ../../gs-core/addons/gs_core addons/gs_core`); everything else is duck-typed.

Also requires **GameSpice Profile** (`GSProfileSet`, `GSProfile`, `GSProfileRuntime`, split from GameSpice Core): link `addons/gs_profile` next to `addons/gs_core`.

- All profile rules (validation, revisions, audit, save) belong to `GSProfileRuntime`; do not copy them here.
- The HTTP server is GameSpice Core's `GSHttpServer`; `GSWorkbenchHttp` only mounts routes on it. The page is `addons/gs_workbench/web/index.html` (one file, no build); an export needs `*.html` in its include filter. The host calls `GSWorkbenchHttp.poll()` from `_process`.
- `GSWorkbenchPanel` is the in-game panel: it binds GameSpice Menu's `GSProfileEditorScreen` (duck-typed, so GameSpice UI and GameSpice Menu stay optional) to the api, so Apply, Reset and `save_to_server()` take the same permission path as HTTP. `tools/panel_shot.gd` needs GameSpice UI, GameSpice Menu and GameSpice Settings linked into `addons/` (gitignored).
- `GSWorkbenchSpawnEditor` is the point-and-click spawn authoring mode (a Node3D; the game gives it `ray_fn`, a camera and the map's points): click adds or selects, Q/E turn, T team (1..`team_count`), V enable, F toggles the click tool between a player spawn and a flag stand (1..8 pick its team; a team owns one flag stand and placing again moves it), G turns the selected point into a flag stand or back, [ ] weight, M move to aim, Delete. Each edit goes through the api into the `spawn` profile of the map (`points.<id>`, gs-spawn's `GSSpawnOverrides` format) and saves to the server tier. Duck-typed to gs-spawn.
- `GSWorkbenchOverlay` is the in-game window (toolbar over the editor) and `GSWorkbenchExport` the tuning round trip: it writes only values differing from `GSWorkbenchApi.baseline_value` (the value seen before the session's first edit) into `cfg/game/<game>/<kind>/<id>.yml`, a zip and a clipboard bundle, and imports any of the three through `api.handle`. Hosting is GameSpice Game's `GSGameWorkbench`.
- `GSWorkbenchScope` tags a set with owner/side/requires/listed (set meta, so `add_set(set, label)` hosts keep working); the overlay rebuilds its sections from `GSWorkbenchScope.sections(api, labels)` on every open. `GSWorkbenchSetView` (kind `<base>@<part>`) lists a group member under its own heading; `GSWorkbenchApi` keeps views out of the runtime and rewrites their kind to the base kind for edits (`kinds()` excludes views, `all_kinds()` includes them). Selftest: `_test_scope`, `_test_views`.
- `GSWorkbenchPublish` (and the CLI `tools/publish_avatar_content.gd`) uploads a wearable, action or avatar GLB (the overlay's "Make wearable" form, `GSWorkbenchWearableForm`, does wearables; the token comes from a file) to the site's `/api/avatar/v1/publish` with a creator token; the site validates and moderates, this only pre-checks fields and size. Suite: `examples/publish_selftest.tscn`.
- Secrets (admin token, TLS key, creator token) are read from files only, never env or argv.
- Validate: `heavy -- godot --headless --path . --import`, parse every `.gd` with `--check-only`, then `heavy -- godot --headless --path . res://examples/workbench_selftest.tscn`.
- `GSWorkbenchApi.forward` (Callable(req)) repeats each applied write elsewhere: a connected client's panel edits its local copy and forwards to the server, where gs-game's `GSGameWorkbenchRemote` checks it again (gs-game `docs/workbench.md`).
- `GSWorkbenchIdentity` is a thin subclass of gs-core's `GSAdminIdentity` (needs gs-core API 29; the gate logic lives there) that gates `api.identity` by duck-typing (resolver Callable, uid and group allowlists, optional fallback permit); keep it free of gs-auth and gs-console references. CI is the shared dot-ci `@v1` (`.github/workflows`).
- Extension points: `GSWorkbenchHttp.mount_extension(prefix, handler, flag)` serves a route prefix behind the same bearer token and lockout (`handler(actor, req) -> GSResult`, called only when `api.permits(actor, flag)`), and `GSWorkbenchApi.add_flag(flag)` lets the admin token hold a new flag. An addon built on them lives in its own repo; nothing here may name it. Example: a neutral `/api/things` route is exercised in the selftest's "extension routes" section.
- `GSWorkbenchApi` rate limits writes per actor (`write_limit` per `write_window_sec`, default 120 per 10 s, 0 disables) with `CODE_RATE_LIMITED`; reads are not counted.
- Page registry: `GSWorkbenchHttp.register_page(id, title, html, flag = "")` serves an addon's own page at `/pages/<id>` (no token for the HTML; it calls its mounted routes with the token) and lists it in the token-gated `GET /api/pages`, which the main page shows as header links. The flag hides it from tokens lacking it. Selftest: "page registry".
